## 推荐组合与推进顺序

1. **基线与材质阶段**：锁定同一曝光/镜头，先试 C2、C3 和 C7。每项独立开关并生成原版/单项/组合截图。保留 demo 的布局、美术素材与控制器。
2. **反射阶段**：先实现 C1 的地面一层；确认递归、裁剪、像素过滤和性能，再扩展到可见水面。不要直接复制 three.js 的三套额外视图而忽略成本。
3. **间接光与雾阶段**：分别比较“SSIL + emitter”“SSIL + SDFGI”“三者低强度混合”，再决定 C5 的散射路径。每次保持整体曝光，避免用提亮伪装细节改善。
4. **地形和动态验收**：加入 C8；检查边缘、透明水、坡道、桥、角色遮挡和镜头移动。高质量档与运行档可以不同，但都必须记录实际成本。

Godot 中的目标是复用自己的场景系统与原生光照，移植 three.js 对“反射完整性和局部颜色映染”的设计。SubViewport 能提供额外视图；反射平面的裁剪/剔除仍需要具体原型验证。当前没有证据保证仅调几个参数就能达到 three.js 的倒影完整度。

## 审查发现

### F1 / P2：three.js 帧率统计会掩盖低帧率

位置：`benchmark/threejs/src/main.js` 的 `frame()` 与 `fpsAcc`。

`dt = Math.min(clock.getDelta(), 1 / 20)` 同时用于游戏逻辑和 FPS 累计。若真实 10 fps，每帧约 0.1 秒却只累计 0.05 秒，统计会趋近 20 fps。该上限用于控制运动步长合理，但性能统计应使用原始墙钟时间。`scripts/bench.mjs` 直接读取该统计，因此下一轮性能比较前应修正，并报告帧时间中位数、P95 和启动/预热成本。本轮没有据此给出新 FPS 结论。

### F2 / P2：截图 ready 不等于素材完整就绪

位置：`benchmark/threejs/src/main.js` 的截图模式纹理等待与 `captureAll()`。

纹理等待达到次数上限后仍设置 `__ready`，没有把资源加载失败作为截图失败；保存 PNG 的 fetch 也没有检查 `response.ok`。服务器返回失败时仍可能设置 `__done`。新实验需要把资源管理器的失败、HTTP 状态和保存结果纳入成功条件。本次额外监听了失败请求/HTTP 状态，并在外部目录检查了实际 PNG，因此本次五张图的成功有独立证据。

### F3 / P2：现有参考条件混合了镜头、等待、素材表现和外围构图

- demo 主场景 FOV 30°；两个 benchmark 都是 25°。同一玩家坐标不能自动保证同一构图。
- demo 的 capture 仅等 40 帧；Godot benchmark 等至少 150 帧且至少 3 秒；three.js 等 150 帧。静态截图时间与粒子相位不一致。
- shot 4 坐标位于河道：Godot benchmark 取水面站高，three.js fallback 取河床。两版 README 已记录此偏差，不能用这一张的角色高度差评价阴影质量。
- three.js 生成了外围台地、道路和多级瀑布；Godot 使用外部低地、松林与山脊。重截的高地视角差异明显，有一部分美感来自构图和远景内容。
- three.js 粒子使用 Math.random，未固定种子；当前不是可逐像素复现的实验。

解决方法：新增受控试验场景，而不是直接修改历史 benchmark 的提示词与截图。统一实际相机世界变换、玩家脚底高度、分辨率和外围内容，固定随机种子及采样时刻，另保留原 demo 镜头作为产品展示组。

### F4 / P2：模型比较的工具权限不对称

`benchmark/prompt.md` 限制 Godot 不安装第三方插件，允许 three.js 任意 npm 包；实际 three.js 使用了 AO 与后处理库。因此它比较的是“模型 + 技术栈 + 可用生态 + 实现选择”的综合结果。单次结果无法分离 JS 熟悉程度、库的现成功能和模型随机发挥，更不能反推出训练语料比例。

### F5 / P3：透明水面与 SSR 的目标不匹配

demo `shaders/water.gdshader` 写入 ALPHA，使用透明路径和屏幕深度；Godot SSR 不能反射透明几何，透明表面也不应被当成完整 SSR 倒影的可靠基础。Godot benchmark 改用不透明水面，three.js 透明水面显式采样额外的平面反射。这三者要单独比较。候选 C1 可保留透明水；另一条候选是改为不透明水 + SSR，但会牺牲可见河床，不能视为同等材质。

### F6 / P3：参数权威来源需要集中

demo 的 ArtDirection 在 ready 时覆盖部分 Environment/材质值。调环境资源后如果没同步 ArtDirection，运行结果可能与编辑器预期不同。集成时应将新参数挂到总控，并在采样时输出“最终有效值”。当前 saturation = 1.97、bloom = 0.25 是总控中的有效设定，不能只依据 shader 默认值解释画面。

## 如何探究 AI 在哪种技术栈下表现更好

建立两条独立实验线，避免后续集成污染对模型原始能力的判断：

### A：模型在技术栈中的成图能力

| 条件 | 建议 |
|---|---|
| 因变量 | 首次成功率、各项光影盲评、达标率、完成时间、token、修复次数、帧时间和明显伪影 |
| 模型 | 同一个确定版本与思考设置；每次新会话；保留完整日志和用户干预记录 |
| 重复 | 每个模型每种技术栈至少 5 次，尽量随机安排顺序；报告中位数、范围和失败样本 |
| 基础档 | 统一功能要求与时间/token预算；Godot 内置功能，three.js 核心库及其官方 addons；明确允许哪些库 |
| 生态档 | 两边都允许预先公布的插件/库；记下实际使用项。分别报告，不与基础档混算 |
| 场景 | 相同素材、布局、相机世界变换、玩家高度、边界内容；生成前后校验素材和布局哈希 |
| 采样 | 相同 1280×800；都满足至少 150 帧和 3 秒、确认资源完整；固定粒子时间或另评动态视频 |
| 视觉评分 | 用原 evaluation 的维度，但把光源本体/光晕/光池/倒影/映染分别计分；匿名随机排列；可读性和克制同样评分 |
| 性能 | 同一机器和电源状态；记录浏览器/引擎/后端；墙钟帧时间，排除首次编译并单列冷启动；不同后端结果表述为完整工具链成本 |

基础档不是语言能力的纯测量：库 API、渲染器和调试工具仍然不同。更窄的语言/API 研究可以额外安排固定算法移植任务，例如同一 emitter GI 公式、同一平面反射验收要求，比较实现正确率与修改成本。

### B：Godot 的画面改善上限

固定一份 Godot demo、固定 Godot 4.4.1 与硬件，分别应用 C2/C3、C1、C4、C6/C5。做逐项开关实验并保存画面和性能。该线允许借鉴已有实现，是工程优化实验，不纳入“模型单次从零生成”的评分。

若 Godot 在统一构图下补上反射和发光源分工后明显进步，即说明现有 Godot 结果受实现策略影响；若仍落后，应进一步定位到裁剪、材质、散射、色彩流程或性能预算，而不能直接归因为模型训练量。

这些短时样本中，FPS 下降约 6%～9%，镜像视图自身的平均 GPU 时间约 0.52～0.60 ms。当前设备距离 60 FPS 的 16.67 ms 帧预算有较大余量。GPU 时钟会随负载变化，不能简单将不同模式的 GPU 时间相加，也不能将本次结果推广到其他设备或 D3D12。

这是额外视图成本探针，尚未将反射纹理绑定到水面 shader，也未验证反射裁剪、图像正确性或移动中的稳定性；不能视为最终集成后的性能保证。测试保留原有主视图效果，实际替换之后可能减少部分旧效果，也可能增加采样和混合成本。

优先实现水面自身的流动法线、深浅色和岸边泡沫；平面反射从可见水面的一张半分辨率视图开始。同一高度的水块共享视图，不同水位按可见性选择；若两个水位同时可见，限制一张视图会牺牲另一个水位的准确反射，应作为明确的质量档位。水面离开画面后停止更新，保留总开关和质量设置。宽高减半只将像素数量降为四分之一，不代表整个反射成本也降到四分之一，因为场景提交和阴影等开销仍存在。
